## 1. 需求与现状分开

用户希望：手机与实体互动形成完整链路；以“能量”呈现相关状态，考虑充电动画；研究日常 hook、定时行为、音量滑杆及升级能力；账号与角色数据在云端。

已确认采用“能量”作为呈现方向，不把用户问题写成“远程唤醒、音量控制、定时播放、OTA 已完成”。尚待确定：桌面常在线与电池节能的模式选择、能量是否包含独立玩法数值、硬件定时唤醒的具体场景、默认音量及各功能批次。提出方案不等于功能批准上线。

## 2. 当前 20 分钟深睡如何唤醒

现状：无活动 20 分钟深睡，录音/等待回复/播放/按键会更新活动时间。插 USB 也执行闲置深睡。睡前停止音频、WSS、WiFi、BLE；仅启用 GPIO3 低电平按键唤醒，不启用 USB 或定时唤醒。

用户路径：按一下实体键 → 松开 → 启动、恢复 WiFi/WSS → ready → 再按住说话；唤醒的第一次按键不会作为录音输入。

- 深睡中：App 远程互动、云消息、BLE 扫描均不能唤醒；USB 插入也不能唤醒。设备没有接收网络包的工作链路。
- 纯电池低于 3.6V 连续 3 秒也深睡；低电压睡眠后需 3.8V 或 USB 才允许运行。不是 App 游戏能量能解除的保护。
- 云端目前没有睡眠原因上报；断线只能表示未连接，不能可靠判定“睡着了”。建议操作文案：“按一下手办按键，再等待连接”。

待评审方案：桌面模式在 USB 下保持业务连接，评估 Modem-sleep/自动 Light-sleep 减少耗电；电池模式保留深睡保护与明确的物理唤醒。Modem-sleep/自动 Light-sleep 的网络保活并非“从 Deep-sleep 收到远程包”；需要电源策略、音频时钟、WSS 保活和延迟/电流实测。当前 WIFI_SLEEP_OFF=true，并未实现上述模式。

不建议用云端反复保活假装用户活动来绕过 20 分钟策略。应显式定义工作模式、活动分类和耗电预算。

## 3. BLE 配网、WiFi 连接、账号绑定是三件事

BLE 是初始或重新配网的配置通道：App/小程序扫描 AIFIG_ → Security 1 加密握手 → 写 SSID/密码 → 设备存 NVS → 重启 → 自行连接 WiFi/WSS。

后续通常是：App → HTTPS 业务 API → 云端 → 设备 WSS；BLE 不是已存在的常驻远程聊天通道，也不会自动成为音量控制通道。已有配网仅提供 WiFi 配置，不提供服务器地址/设备 PSK 动态配置。

“WiFi 配置成功”可作为手边网络配置成功；“设备服务连接成功”“账号绑定成功”仍需独立确认。成功后设备会重启，须验证手机正确处理正常 BLE 断开，不能把它误报为配置失败。

云端是用户账号、设备归属、角色实例、档案、玩法进度的业务事实源。设备本地存 WiFi 凭据/设备身份和必要配置；App 保存认证凭据与必要缓存。默认不把家庭 WiFi 密码上传云端，不把用户账号密码/完整档案写入设备。

绑定目标流程：登录 → 获得设备标识 → WiFi 配置 → 验证设备实际身份与用户认领权限 → 云端确认归属 → 显示已绑定。现有 /devices/claim 仅为客户端调用草案；实际身份校验、认领/解绑与 API 服务待实现。Security 1 无 PoP 的加密握手不等于证明设备归属，不等于云端账号授权。

## 4. “能量”及补能动画

采用用户提出的能量呈现方向；它不能掩盖数据来源。

- **设备能量**：实体供电/电池状态的角色化表达。可以用低/正常/充足等分档，具体门槛需电池负载与充电状态下校准；当前只有 VBAT 与 USB 本地读数，没有百分比。先补上报、云缓存/API、采样有效性与更新时间。
- **角色玩法能量**：若玩法需要消耗/恢复，应作为独立云端游戏规则；是否采用、如何恢复仍待设计。不得同真实电量共用字段或显示来源不明的同一条进度条。
- **补能动画**：收到有效 USB 检测后可表现“已接电源”的补能/供电动画；STAT 未接主控，USB 检测不能证明电池正在充电或已经充满。禁止仅因 App 点了按钮就显示实体在充电。
- USB 无电池时 VBAT 无意义；低电压、无电池/未确认、失效读数、数据过期均需单独处理，不能显示 0 能量或虚假上涨。
- 没有真实上报时隐藏设备能量或显示未知，不做演示数值充当实测。

此方向仅针对设备状态与未来明确的玩法规则，不恢复亲密度、关系等级或连续签到压力条。若独立玩法数值与旧“无数值化”约束冲突，需单独评审后更新规则。

## 5. 日常 hook、远程互动与定时行为

先区分事件发生、内容生成、设备接收、实际播放四个事实；不能“云端生成了”就记为“手办已经说过”。用户要求场景触发，仍遵循低负担、不随机催聊、不惩罚错过的方向。

### 5.1 当前源码的额外阻断

session.cpp 的 AUDIO_BEGIN 只在 WAITING 接受，IDLE/RECORDING 等状态都会忽略。现有协议服务于“按键录音 → 等待回复”，并无通用事件播放命令。设备在线也不等于云端可随时让它开口。

### 5.2 建议最小链路（待实现与评审）

App 用户操作/游戏事件/用户允许的日常时点 → 云端建立事件 → 根据角色规则生成内容 → 检查归属、在线和设备能力 → 下发明确的事件播放请求 → 设备在允许状态播放 → 回传已接受/开始/完成/失败/取消。

设备侧须增加独立于语音问答的事件播放入口与状态转换、事件标识、过期检查、重复拒绝、音频接收规则、按键打断与录音优先。服务端须提供路由、权限、安静时段、限频、期限和执行回执；App 只在回执确认后表现实体执行成功。

建议规则：手动触发离线即提示不可执行，不在用户很久后意外播放；非强时效事件可等下次用户主动唤醒后展示/领取；时效事件过期跳过；重复交付不重复播放；录音、配网、升级中不强行插播。细分规则按具体玩法再评审。

### 5.3 三种定时方案

| 方案 | 实现位置 | 设备睡着时 | 当前状态 |
|---|---|---|---|
| 云端定时 | 服务器任务持有日程，设备在线时发送事件 | 无法唤醒，过期跳过或等待主动连接 | 调度、事件播放链路未实现 |
| 设备本地定时 | 缓存已确认日程/内容，启用 RTC timer 唤醒，维护时间与有效期 | 定时醒来，必要时联网校时/取内容后执行 | 当前只开 GPIO 唤醒，无定时任务/缓存/校时闭环 |
| App 本地通知 | 手机系统提醒，用户打开 App 或按实体键继续 | 只能提醒手机，不唤醒实体 | iOS 有通知权限入口，不等于已有定时任务 |

RTC 定时唤醒可利用现有芯片能力，不必然换板；绝对时刻、时区变化、重启断电、时钟漂移、失联、低电量拒绝执行必须设计。供电稳定的桌面模式适合评估云端定时；电池模式先以按键和用户允许的事件为主。不要承诺离线固定时间一定开口。

## 6. 音量滑杆

已有 setOutputGain()/getOutputGain()，运行时增益范围 0–256；当前无解析音量指令、回执与 NVS 持久化，App 滑杆尚不能操作实体。

可基于现有函数扩展：App 0–100% → 经过新板实测限定的安全增益 → 云端授权下发 → 固件设置并回执 → App 显示实际值；完成拖动后保存 NVS，启动恢复，避免每个拖动点写 Flash。单位映射不承诺线性响度，不能无测量把最大值固定映射为 256。

待验收：静音/最大值、供电压降、失真、录音/播放并发、超时与设备离线、连续拖动顺序、重连同步、重启保留。离线时禁止显示调整成功。BLE 本地调音量是另一个新增服务/特征设计，不复用配网端点强塞命令。

文档将其列为可操作滑杆候选需求，待产品批次与三端契约批准；历史 MVP1 无音量控制为旧交付范围，不宣称已被代码解除。

## 7. 双 OTA 分区是什么

4MB Flash 中 ota_0 与 ota_1 各 0x1E0000（1,966,080 字节，1.875 MiB）；otadata 记录启动槽，NVS 另存配置。两槽用于轮换放固件，不是双芯片、双系统并行，也不是两个角色位置。

完整升级流程：运行槽 A → 下载适配当前硬件的固件到 B → 校验完整性/可信来源 → 更新启动槽 → 重启 → 新固件自检确认 → 若配置并实现了回滚机制，失败回旧槽。下一次反向轮换。不能覆盖正在运行的镜像，也不能把“另一个槽存在”当作自动回滚已完成。

当前只提供分区；未见 OTA 下载/升级入口/健康确认/自动回滚策略实现。设备需要在线、足够供电且不在录音或播放。升级必须检查硬件型号、固件大小/版本、断电恢复和 NVS 兼容。Arduino 旧分区向当前 IDF 布局迁移涉及引导程序/分区表，不能直接承诺用普通应用 OTA 完成首次迁移。

App 将来可作为版本/升级发起与状态显示端；下载可由设备经 HTTPS 完成，BLE OTA 属另一交付方式，不因分区存在而自动具备。

## 10. 随身使用、深睡与升级的补充说明

### 10.1 有电池后的随身使用

电池解决离开 USB 的供电问题，已有随身使用的硬件基础；不等于独立联网或随身成品已验收。现有设备没有蜂窝联网实现，语音对话仍依赖可用 WiFi/WSS/云服务。外出可使用已配网的手机 2.4GHz 热点，热点和蜂窝网络费用/耗电由手机承担；热点兼容性与重连必须实测。

| 场景 | 当前判断 |
|---|---|
| 电池供电 + 已配置且可用 WiFi/热点 | 具备云对话链路条件，待新板联调 |
| 电池供电 + 没有可用网络 | 不能运行当前云端 ASR/LLM/TTS；不是离线聊天设备 |
| 深睡状态 + 手机热点开着 | 不会因网络可用自动醒来，需实体按键 |
| 手机 App 使用角色/3D/游戏 | 可独立于实体设备；在线云业务与本地能力分别判断 |

便携实物仍待电池续航、充电温升与保护、掉网/热点重连、声孔/装配固定、USB 可达性和携带中的误触验证。未量测前不提供“可用几小时”承诺；现有无活动深睡不能防止所有包内按键误触。无需为随身使用重新定义角色关系或强迫增加聊天。

### 10.2 深睡是停止接收，不只是屏幕/声音关闭

20 分钟从最近一次实际活动计算，不是从联网起算。实体按键与录音/等待回复/播放更新时间；设备仅在线、WiFi 心跳或云端仍有角色内容不等于用户活动。还有独立的低电压深睡保护。

深睡前停止 WSS/WiFi/BLE 和音频，CPU 不再运行通常的会话循环。云端没有能到达设备的接收通道，所以不能把推送当作唤醒指令。当前仅 GPIO3 唤醒；恢复执行要启动并重连，并非保留旧 WSS 会话。

未来若需要远程互动，候选是保持网络可达的桌面/连接待机模式，而不是深睡中直接接收网络消息。也可新增周期 RTC 唤醒查询事件，但只能在下一次查询时执行，延迟和耗电与查询周期相关；该方案非即时云端唤醒，尚未选定或实现。用户指定的定时本地行为可独立评估 RTC 定时唤醒。

### 10.3 第 4 项 hook/定时方案的落档状态

本文 §5 和 §8 已记录：当前 WAITING 音频门槛、独立事件播放入口、云调度与本地定时两种路径、执行回执、按键优先、错过与过期处理。任务仅为待设计/待实现，不将需求讨论当作设备已经可以主动播报。不通过虚构 turn_start/turn_end 或取消旧过期音频保护来绕过状态机。

### 10.4 双 OTA 的产品价值

OTA 是通过网络更新设备固件。双槽允许在运行当前固件时，把新版写进另一个槽，减少下载中断对现用镜像的影响；完成正确的启动与健康确认/回滚实现后，可在新版本启动失败时恢复旧版本。两个槽预留本身不提供这些完整保障。

它的产品价值是：未来为已交付设备升级音量控制、场景播放、电量上报、电源策略和 bug 修复，无需每次拆机连接 USB 烧录。它不增加电池容量、不提供联网、不使深睡设备远程可达，也不代表升级 App 就自动升级固件。云端玩法变化未必需要固件升级；只有本地协议/驱动/行为变化才需要。

现阶段有两个槽，但无可用 OTA 服务；首次新分区布局迁移仍需按烧录方案执行。OTA 接通前要验证升级供电、镜像可信性/硬件匹配、失败恢复和 NVS 兼容，不能承诺现有 WiFi 或绑定数据在任何版本迁移中都自动保留。
